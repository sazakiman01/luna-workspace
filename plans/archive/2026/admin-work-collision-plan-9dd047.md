# แผนแก้ไขข้อมูลซ้ำซ้อนใน Delivery Hub Admin Work
สรุป: วิเคราะห์สาเหตุข้อมูลชนกันใน Admin Work แล้วออกแบบแนวทางป้องกันและทำความสะอาดข้อมูลที่ซ้ำก่อนยืนยันวิธีแก้ถาวร

1. วิเคราะห์กระบวนการบันทึกปัจจุบัน
   - ตรวจสอบ AdminWorkModal และ adminWorkService เพื่อทำความเข้าใจ flow การโหลด/บันทึกข้อมูลและ cache ที่ใช้
   - ทำ mapping ว่ามีโอกาส race condition หรือการ submit ซ้ำจากหลายคน/หลาย tab อย่างไร
2. ตรวจสอบข้อมูลซ้ำใน Firestore
   - ออกแบบแนวทางตรวจจับ entries ที่มี (userId, date, category) ตรงกันหลายรายการ
   - ประสานกับผู้ใช้เพื่อได้ตัวอย่าง/ช่วงเวลาที่มีปัญหาเพื่อยืนยัน pattern
3. ออกแบบแนวทางป้องกันการชนในอนาคต
   - พิจารณา hash key หรือ composite ID ฝั่ง client, optimistic locking, หรือ server-side merge ก่อนเขียน
   - เสนอ UX guard เช่น lock cell ระหว่างบันทึก, แจ้งเตือนเมื่อข้อมูลเปลี่ยนจากผู้ใช้คนอื่น
4. วางแผนทำความสะอาดข้อมูลปัจจุบัน
   - กำหนด script/service เพื่อลบ/รวม entries ที่ซ้ำโดยยึดชั่วโมงล่าสุดหรือผลรวมที่ถูกต้อง
   - สร้าง checklist การทดสอบเพื่อยืนยันว่าแผนถาวร + cleanup ทำให้ข้อมูลเสถียร
